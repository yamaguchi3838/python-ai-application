# レポートフォーマット

生成するレポート(`security-report.md` 等)は以下の構成にする。指摘がないカテゴリは「特筆すべき指摘なし」と一言書いて省略せず残す(項目自体を見た上で問題なしと判断したことが分かるようにする)。

```markdown
# セキュリティチェックレポート: <アプリ名>

実施日: <YYYY-MM-DD>
対象: <確認したディレクトリ/リポジトリ>

## サマリー

- High: <件数>
- Medium: <件数>
- Low: <件数>

<全体を2〜3文で要約。最も優先して直すべき点を先頭に。>

## 指摘事項

### [High] <指摘のタイトル>

- **該当箇所**: `path/to/file.py:42`
- **問題**: <具体的なコード/設定を引用しながら何が問題か>
- **想定される悪用シナリオ**: <攻撃者が何をできるか、一言で>
- **修正案**:
  ```python
  # 修正後のコード例
  ```

### [Medium] <指摘のタイトル>
(同様の構成)

### [Low] <指摘のタイトル>
(同様の構成)

## カテゴリ別チェック結果

| カテゴリ | 結果 |
|---|---|
| 1. シークレット・APIキー管理 | <指摘あり(上記参照) / 特筆すべき指摘なし> |
| 2. プロンプトインジェクション | ... |
| 3. Streamlit特有のリスク | ... |
| 4. データの取り扱い・コスト濫用 | ... |
| 5. 依存パッケージの脆弱性 | ... |
| 6. アクセス制御・公開範囲 | ... |

## 手動確認が必要な項目

<recon スクリプトや静的な読み込みだけでは判断できず、デプロイ方法や運用方針の確認が要る項目。例: 「公開デプロイの予定があるか」「pip-auditが未インストールのため依存脆弱性は目視確認のみ」>
```

要点:
- 指摘のタイトルは「〜に注意」のような曖昧な表現ではなく、「APIキーがエラーメッセージに露出する」のように具体的な事象名にする。
- 修正案は可能な限りそのリポジトリのコードに対する差分イメージが分かる形にする(理想は実際に動くコード)。
- 「手動確認が必要な項目」を必ず設ける。ツールや静的読み込みだけでは判断できない(運用・デプロイ方針に依存する)項目を無理に White/Black で判定せず、正直に「要確認」として書くほうが信頼できるレポートになる。

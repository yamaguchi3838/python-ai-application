# チェックリスト

各項目について「該当するか」「なぜ問題か」「どう直すか」をセットで確認する。すべてのアプリに全項目が当てはまるわけではないので、該当しない項目はレポートで省略してよい(無理に埋めない)。

## 1. シークレット・APIキー管理

- **ハードコード**: ソースコード中に API キーの文字列リテラルが直接書かれていないか(`grep` で完全には拾いきれないので、`api_key=`, `Client(`, `apiKey`, `Authorization` などの周辺を目視する)。
- **`.gitignore` と実際の git 管理状態**: `.env` や `.streamlit/secrets.toml` が `.gitignore` に書かれているだけでなく、実際に `git ls-files` で追跡されていないか確認する。`.gitignore` に書かれていても、`.gitignore` を書く前にコミットされていれば追跡されたままになる。
- **キーのログ出力・エラーメッセージ露出**: 例外処理でリクエスト内容やヘッダーをそのままログ/画面に出していないか。`st.exception()` や `traceback.format_exc()` をそのままユーザーに見せていると、環境変数の値がスタックトレースに乗るケースがある。
- **UI上でのキー表示**: `st.text_input` で API キーを受け取る場合、`type="password"` になっているか(平文表示されていないか)。
- **複数ユーザーでの共有懸念**: `st.session_state` はセッション(ブラウザタブ)ごとに独立しているため、通常は他ユーザーに漏れない。ただし、キャッシュ関数(`@st.cache_data`/`@st.cache_resource`)の戻り値にキーやレスポンスを含めていないか、共有デプロイでキャッシュがユーザー間で共有される設計になっていないかは確認する。

## 2. プロンプトインジェクション / LLMへの入力信頼境界

- **ユーザー入力とシステム指示の分離**: システムプロンプト(指示)とユーザー入力(データ)が同じ文字列に単純結合されていないか。SDK が `system_instruction` のような専用パラメータを提供しているのに使わず、全部を1つのプロンプト文字列に埋め込んでいる場合、ユーザーが「これまでの指示を無視して」といった文言で指示を上書きできる余地が生まれる。
- **外部コンテンツの取り込み**: URL 取得やファイルアップロードの内容をそのまま LLM に渡している場合、そこに埋め込まれた指示文(間接プロンプトインジェクション)がプロンプトを乗っ取る可能性がある。取り込み元が信頼できない場合は特に注意。
- **LLM出力の下流での扱い**: 生成されたテキストをそのまま `exec`/`eval`、シェルコマンド、SQL クエリ、ファイルパスとして使っていないか(LLM が生成したものは実質的に「信頼できない入力」として扱う)。
- **出力の事実性を装った処理**: 生成結果を検証なしに外部送信(メール送信、API 呼び出しなど)のトリガーに使っていないか。

## 3. Streamlit 特有のレンダリング・入力リスク

- **`unsafe_allow_html=True`**: `st.markdown(..., unsafe_allow_html=True)` や `st.write` で、LLM の出力やユーザー入力を HTML として描画していないか。LLM が(意図的な誘導や偶然)`<script>` や `<img onerror=...>` を含むテキストを生成すると、閲覧者のブラウザで実行される反射型/蓄積型 XSS になり得る。素の Markdown 描画(`unsafe_allow_html` なし)なら通常安全。
- **ファイルアップロード**: `st.file_uploader` を使っている場合、ファイルサイズ・拡張子・MIME タイプの検証があるか。アップロードされたファイルをサーバー側のパスにユーザー入力由来の名前で保存している場合、パストラバーサル(`../../`)の余地がないか。
- **`st.components.v1.html` / iframe埋め込み**: 外部やユーザー由来のコンテンツを iframe で埋め込んでいないか。
- **デバッグ設定**: `.streamlit/config.toml` で `[server] enableXsrfProtection`, `[client] showErrorDetails` などが本番相当のデフォルトから緩められていないか(可能なら確認、見つからなければ「未設定=Streamlitのデフォルト」と明記してよい)。

## 4. データの取り扱い・プライバシー・コスト濫用

- **機微情報の外部送信**: ユーザーが入力した個人情報や社外秘情報が、そのまま LLM API(外部の第三者サービス)に送信される設計になっていないか。マスキングや利用目的の明示があるか。
- **ログへの平文記録**: プロンプトやレスポンス全文をログファイルや監視サービスに平文で残していないか。
- **入力長・レート制限**: プロンプトの長さやリクエスト頻度に上限がないと、悪意あるユーザーが大量にリクエストを送って API コストを消費させられる(公開デプロイの場合は特に重要)。
- **キャッシュの有無**: 同一入力に対して毎回 API を叩いている場合、意図的な連打で容易にコスト濫用できる。

## 5. 依存パッケージの脆弱性

- **バージョン固定**: `requirements.txt`/`pyproject.toml` で `>=` のみ指定されていて上限がない場合、将来の破壊的変更だけでなく、意図せず脆弱なバージョンから外れる/固定できない状態になる。完全な固定を強制する必要はないが、指摘としては残す。
- **既知の脆弱性**: `pip-audit` や `safety` がインストールされていれば実行して結果を反映する(`pip-audit -r requirements.txt` 等)。ツールがなければ、主要ライブラリ(streamlit, 各LLM SDK)が既知の重大 CVE を持つ古いバージョンに固定されていないか目視で確認し、確証がなければ「要手動確認」として報告する。

## 6. アクセス制御・公開範囲

- **認証の有無**: アプリが社内共有・一般公開される想定なのに、Streamlit 自体にも前段のリバースプロキシ等にも認証機構がない場合、誰でも API キーの持ち主のコストでLLMを呼び出せてしまう。
- **ページ単位の権限**: マルチページアプリで、特定ページ(管理者向け機能など)に閲覧制限がかかっているか。
- **CORS/XSRF**: `.streamlit/config.toml` の `enableCORS`, `enableXsrfProtection` が意図的に無効化されていないか。
